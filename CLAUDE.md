# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Clocky — a desk clock firmware for ESP8266 (ESP12-F, board id `esp12e`) or ESP32 (Wemos Lolin32), built with PlatformIO / Arduino framework. It syncs time over NTP with DST correction, drives a 128x32 SSD1306 OLED, chimes hourly and on a settable alarm via a piezo beeper, has a capacitive touch pad (no physical button) for stepping through its three display modes (desk clock → stock indexes → sleep), shows the Dow / S&P 500 / Nasdaq in stock mode (fetched over HTTPS from Yahoo Finance), and serves a custom web dashboard (via `ESPAsyncWebServer` + a JSON REST API, embedded HTML/CSS/JS — no ESPUI) for Wi-Fi credentials, time zone, alarm, and OTA firmware updates.

The project was recently converted from an Arduino-IDE sketch (`.ino` files) to a proper PlatformIO layout — `.ino` files were renamed to `.cpp`, and the git repo root was moved from `src/` up to the project root so `platformio.ini` is tracked alongside `include/`, `lib/`, `test/`, and `src/`.

## Commands

Build, upload, and monitor with the PlatformIO CLI (env name is `esp12e`):

```bash
pio run                      # build
pio run -t upload            # build and flash over serial
pio run -t upload -t monitor # flash then open serial monitor
pio device monitor            # serial monitor only (115200 baud)
pio run -t clean             # clean build artifacts
```

There is no test suite configured (`test/` only contains PlatformIO's placeholder README).

`platformio.ini` also has a `touch_tuner` env (not built by a plain `pio run`; `default_envs = esp12e`) for re-tuning the touch pad — see the touch pad paragraph below:

```bash
pio run -e touch_tuner -t upload                                   # replaces the clock firmware until you re-flash esp12e
~/.platformio/penv/bin/python tools/touch_capture.py capture        # sends 's', records until "# done", prints stats
~/.platformio/penv/bin/python tools/touch_capture.py analyse a.csv b.csv   # pooled stats over several runs
~/.platformio/penv/bin/python tools/touch_watch.py --host clocky.local --secs 75 --out x.csv   # over Wi-Fi (needs -D TOUCH_DIAG)
~/.platformio/penv/bin/python tools/touch_watch.py replay x.csv --press 35   # offline what-if on a recording
```

OTA updates (via ElegantOTA) can be pushed from the web UI at `http://clocky.local/update` once the device is on Wi-Fi, instead of a serial upload.

## Architecture

Single firmware image split into modules that communicate through `extern` globals declared in headers (no OOP/singleton pattern — this is a small embedded project, and modules just include each other's headers):

- **`config.h`** — hardware constants only: pin assignments (buzzer, touch pad sensor/driver, status LED), display dimensions, alarm tone frequencies, hostname. Change this file to adapt to different wiring or a different board; the two supported boards (ESP8266 vs ESP32) are distinguished at compile time via `#if defined(ESP32)`.
- **`clocky.h`** / **`Clocky.cpp`** — entry point (`setup()`/`loop()`), owns the shared `Preferences` (NVM) object and the alarm hour/minute/active-days state. (`clocky.h` also declares `dayBuffer`, a `CircularBuffer<float,24>` left over from an earlier feature — currently unused; the debug log's own ring buffer lives in `debug.cpp`.) `runAlarm()` gates the settable alarm (not the hourly chime) on `activeDays`, a `uint8_t` bitmask with bit 0 = Sunday .. bit 6 = Saturday, matching TimeLib's `weekday()` (1=Sunday..7=Saturday) via `activeDays & (1 << weekday(t))`. It fires once per triggering minute (latched on minute-of-day, since `loop()` calls it many times while `second() == 0`), and then plays a looping tune — including in sleep mode — until a touch silences it (`stopAlarmTune()` in the touch handler). The tune is a compile-time choice via `ALARM_TUNE` in `Clocky.cpp` (1 = "The Sailor's Hornpipe", the default; 0 = a short original ditty; overridable with `-D ALARM_TUNE=0` in `build_flags`), stored as an `alarmTune[]` table of `{freq, beats}` notes pitched at or below ~3 kHz for the piezo. Notes are stepped by a `Ticker` callback (`playNextAlarmNote()`), not from `loop()`, because `loop()` is too uneven (the blocking chime and stock fetch) to keep a rhythm. The hourly chime is skipped while `alarmRinging` so the two don't overlap. Aggregates the other modules' headers. The display mode is `buttonPressCounter % NUM_MODES` (`currentMode()`: `MODE_CLOCK`, `MODE_STOCKS`, `MODE_SLEEP` — each touch steps to the next); there is no separate mode variable. Stock mode draws via `prepStockFace()` when `stocksFresh()` (one index per 3 s: rounded value in 12pt, a 9pt one-letter tag D/S/N from the label's first character, and an up/down triangle vs. previous close), otherwise it draws the ordinary clock face (`prepClockFace()`), so any fetch failure degrades to the plain clock. The hourly chime is muted only in `MODE_SLEEP`.
- **`wifi_manager.h`** / **`wifi_manager.cpp`** — non-blocking Wi-Fi connection state machine (`WifiState`: disconnected/connecting/connected/AP mode), stepped once per `loop()` from `handleWiFi()`. Falls back to a self-hosted AP named `HOSTNAME` after `WIFI_MAX_CONNECT_ATTEMPTS` timeouts, so the user can reconfigure via the web dashboard (saving credentials there sets the state back to `DISCONNECTED` to retry — no reboot needed). Logs link up/down transitions with how long the link had been up/down (`humanDur()`).
- **`time_manager.h`** / **`time_manager.cpp`** — NTP client, DST-aware `Timezone` conversion (via the `Timezone` and `TimeLib` libraries), the set of predefined `Timezone` objects the dashboard lets the user pick from, and `tzName()`/`tzCode()` lookups used by the JSON status API.
- **`stocks.h`** / **`stocks.cpp`** — stock-index mode's data. `handleStocks(wanted)` is called every `loop()` and, only while stock mode is selected and WiFi is up, does a **blocking** (~2 s) HTTPS fetch of `^DJI`, `^GSPC`, `^IXIC` from Yahoo's unofficial chart endpoint (`query1.finance.yahoo.com/v8/finance/chart/<sym>?interval=1d&range=1d`; needs a browser-like User-Agent or it returns 429) — once on entering the mode, then every 5 minutes, retrying after 60 s on failure. All three share one TLS connection; prices are pulled out with a plain string search (`"regularMarketPrice":`, `"chartPreviousClose":`), no JSON parse. TLS uses `setInsecure()` (no cert validation — display-only data). `stocksFresh()` is false until a complete fetch succeeds and again once the data is >15 minutes old. **ESP8266 memory gotcha:** with the IRAM 2nd-heap MMU option, the core's BearSSL client tries the IRAM heap first for its I/O buffers and then makes a throwing 16-byte `new` in the same heap; if the buffers leave <~24 bytes free there, the device aborts with "Unhandled C++ exception: OOM". `fetchAll()` works around this by sizing the TX buffer (or temporarily filling the IRAM heap) so the 16 KB RX buffer lands in IRAM with room to spare and the TX buffer falls back to the main heap — re-check this logic if IRAM usage changes much. It also refuses to fetch when the main heap is too low/fragmented rather than risk an abort.
- **`web_server.h`** / **`web_server.cpp`** — owns the single `AsyncWebServer server` instance (port 80) and `setUpWebServer()`, called from `setup()`. `ElegantOTA.begin(&server)` is called right after, on the same server instance, so `/update` keeps working unchanged. Serves the dashboard's HTML/CSS/JS (from `web_assets.cpp`, embedded PROGMEM strings — no filesystem/LittleFS involved) plus a small JSON REST API: `GET /api/status` (polled by the browser every second: time, timezone name/code, RSSI, alarm disabled flag, alarm hour/minute, `activeDays` bitmask, current `weekday` (1-7), stored SSID, AP-mode flag, a `stocks` array of `{n,p,c}` = name/price/previous close that is present only while `stocksFresh()`, debug log tail) and POST actions `/api/alarm` (enable/disable), `/api/schedule` (alarm hour/minute/`activeDays`, persisted via `preferences.putUChar("activeDays", ...)`, default `0x7F` = every day), `/api/wifi`, `/api/timezone`, `/api/settime` (browser pushes its clock once when `apMode` is true, since there's no NTP source to sync from), `/api/reboot` (arms a ~500ms deferred reboot via the `rebootAt` deadline checked in `loop()`, so the HTTP response flushes before the device resets — it does not restart inline). The config-writing routes each mirror what an ESPUI callback used to do (same `Preferences` keys, same in-memory state updates), just invoked over HTTP instead of a control callback.
- **`web_assets.h`** / **`web_assets.cpp`** — the dashboard itself as three PROGMEM string constants (`INDEX_HTML`, `STYLE_CSS`, `APP_JS`). Single-page app with CSS-only card layout (light/dark via `prefers-color-scheme`) and vanilla JS (no framework) that polls `/api/status` on a 1s interval and POSTs actions via `fetch()`. Tabs: Status (time, WiFi signal, a "Markets" section rendered by `renderStocks()` that is hidden unless `/api/status` includes `stocks`, "next alarm" readout computed client-side in `describeNextAlarm()` from `runHour`/`runMinute`/`activeDays`/`weekday`, debug log), Alarm (enable switch, hour/minute, day-of-week toggle buttons built client-side from the `activeDays` bitmask — see `buildDayCheckboxes()`/`applyActiveDays()`), Setup (WiFi credentials, time zone, firmware update link, reboot).
- **`debug.cpp`** — `webPrint()` (printf-style logging that goes to both `Serial` and a circular buffer; on overflow it trims from the front to the next `\n` so the log always starts on a line boundary) and `fetchDebugText()`, which copies that buffer into `charBuf` **non-destructively** (each byte is `shift()`ed off and immediately `push()`ed back). `web_server.cpp`'s `/api/status` handler calls this every request — draining would leave the web log showing only the last ~1s of output, since the dashboard polls once per second.

The touch pad is read via an RC-delay trick by the project-local, reusable library **`lib/TouchPad/`** (no dependencies on the rest of Clocky; see the header comment in `TouchPad.h` for the full rationale). `DriverPin` (D3) charges the pad through a 300k resistor; `SensorPin` (D7) reads it. Key points, each learned the hard way:

- **Measurement:** one rise-time reading every 3 ms (CPU cycle counter + direct GPIO registers, interrupts off, 100 us discharge, 1 ms timeout). `measureNs()` is `IRAM_ATTR` — from flash, an instruction-cache miss mid-measurement added a fixed ~4 us (+45 %) to ~12 % of readings in the full firmware and caused phantom presses (the standalone tuner never showed it because its loop stayed cached). The old 10 ms discharge `delay()` was also the noisiest setting measured (it yields to Wi-Fi right before timing).
- **Filter:** decision on the median of the last 7 readings (21 ms ≥ one 50/60 Hz cycle). Press: median >+35 % over a self-tracking baseline for 15 readings in a row (~45 ms). Release: <+8 %. Baseline tracks untouched readings in fixed point (x256 — in plain ns, slow tracking rounded to zero movement upward), rising with tau ~3 s and falling 16x faster. Held above release for 30 s → becomes the new baseline (an object left by the pad can't latch it "held"). Rises past half the press level that fall back are `nearMisses()` (Clocky logs them, at most once a minute).
- **Timeouts:** an isolated timeout counts as a very *long* reading (strong touch); only 50 in a row (~150 ms) means `stuck()` → untouched, logged by Clocky.
- **Power supply matters most.** On USB (earthed via the PC) everything is clean: hover +3..9 %, taps +60..230 %. On an ungrounded 2-prong wall adapter, the adapter's Y-cap leakage puts 50/60 Hz on the clock's ground, and behaviour depends on **plug orientation**: in one, hovering 0.5–2 cm reads up to +26 % (grazes +51 %, taps +184..228 %); in the other, a touching finger makes readings swing with the mains cycle including timeouts (hence the timeout rule) and Wi-Fi activity right after connecting gives 15–30 ms bursts of 50–1000 us readings with nobody touching (hence the ~45 ms confirm). The +35 % / 45 ms / timeout rules were chosen by replaying recordings from both orientations (`tools/captures/`).
- **Clocky integration:** `touchPad.update()` runs from a 1 ms `Ticker` (`sampleTouchPad()`), not `loop()`, so the pad is still read while `loop()` is blocked; the Ticker only counts presses (`pendingTouches`) and `loop()` acts on them. Even so, the stock fetch's TLS handshake has ~0.5 s stretches where no Ticker runs, long enough to swallow a tap — so `handleStocks()` is only allowed to start a fetch once the pad has been untouched for 3 s (`lastTouchMs`).
- `begin()` learns the baseline, so keep hands off at boot (a wrong baseline self-corrects).

Tuning tools: `tools/touch_tuner` + `tools/touch_capture.py` (guided OLED test, serial, USB only — first-pass tuning, sweeps discharge time); `tools/touch_watch.py` (records over Wi-Fi from `GET /api/touchraw`, the only way to measure on wall power; `replay FILE` re-runs the decision logic offline with `--press/--release/--window/--confirm/--shift`). `/api/touchraw` and a per-press raw-reading log line exist only when built with `-D TOUCH_DIAG` (in `build_flags`; ~2.8 KB RAM).

Persistent settings (Wi-Fi SSID/password, alarm hour/minute, time zone) are stored via the `Preferences` library (NVS-backed key/value store), not `EEPROM.h` directly.

`DEBUG_ESP_OOM` and the IRAM/2nd-heap MMU option are required build flags on ESP8266 when using `AsyncWebServer` — see the `#error`/`#warning` guards at the top of `Clocky.cpp` and the corresponding `build_flags` in `platformio.ini`.

## Repository layout note

`platformio.ini`, `include/`, `lib/`, `test/` live at the repo root; actual firmware source is under `src/`. `src/.gitignore` is a leftover from the pre-PlatformIO layout (generic C++ object-file patterns) and is largely redundant with the root `.gitignore`, which also excludes `.pio/`, `src/build/` (stale Arduino-IDE build output), and `compile_commands.json`.
